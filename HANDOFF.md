## 1. Vision

UniBuzzz is a university-only social platform, launching first at **UCD** (email domain `ucdconnect.ie`), combining: an Instagram/Facebook-style feed, Reddit-style communities, a marketplace, DMs, and a Rate My Professor / Rate My Course reviews section. Architecture is explicitly designed so a second university is a **data change** (a row in `universities`), never a code change. Building web first (React + TS PWA), with a React Native app planned later reusing the same backend and a shared TypeScript package.

## 5. Database & architecture

**Multi-tenancy**: every user-generated table has `university_id`. RLS policies key off `current_university_id()` (a `SECURITY DEFINER` SQL function that looks up the caller's own row) — never a hardcoded university. Onboarding a second school is inserting a row into `universities` with its email domain(s).

**Tables** (chronological via migrations in `supabase/migrations/`):

- `universities`, `users` — core tenant + profile tables. `users.role` (student/moderator/admin), `users.status` (active/suspended/banned) — managed via the admin dashboard's Users page (`/admin/users`). Role changes are **admin-only**; suspend/ban is also **admin-only** (tightened from staff-wide during the admin dashboard build, see §10). Self-escalation is blocked at the trigger level (`prevent_protected_user_field_changes`) — an admin can never change their own role or status, including via the dashboard.
- `reports` — general polymorphic reporting (`target_type`: post/comment/listing/message/community/user), added for the admin dashboard. `review_reports` (below) stays separate/reviews-only rather than being merged in. Resolved only via the `resolve_report(p_report_id, p_decision, p_note)` RPC, which also writes an `audit_log` row. Messages get a **narrow, report-scoped** staff SELECT policy (`messages`/`conversations`/`conversation_participants`) — staff can read a reported message and its participants, never browse DMs generally.
- `audit_log` — append-only (no UPDATE/DELETE policy for anyone). Populated two ways: `AFTER UPDATE` triggers on `users`/`posts`/`comments`/`listings`/`reviews`/`communities` for direct-UPDATE moderation actions, and explicit inserts inside `resolve_report`/`admin_review_entity_submission` for RPC-driven actions. Read via `/admin/audit-log`.
- `posts`, `post_media`, `comments`, `reactions` — feed. `reactions` is **polymorphic** (`target_type`: post/comment, `type`: like/upvote/downvote) — shared by feed likes AND community voting, not two separate systems. `posts.like_count`/`comment_count` are **trigger-maintained**, not computed on read.
- `communities`, `community_members` — Reddit-style. `posts.community_id` (nullable) was added later via `ALTER TABLE` once communities existed. `public` communities are readable without joining; `restricted` ones require membership to read; **posting into any community always requires membership** regardless of type. **Creating one now requires admin approval** (added during the admin dashboard build, see §10): there is no client INSERT policy on `communities` at all any more — a request goes into `entity_submissions` (`type='community'`) and only becomes a real row via the admin-only `admin_review_entity_submission` RPC. Existing communities carry a `status` (`active`/`locked`/`removed`) staff can change from `/admin/communities`; content (name/description/type/slug) is immutable after creation, same convention as everywhere else.
- `conversations`, `conversation_participants`, `messages` — DMs _and_ marketplace chat (same tables, `conversations.type` distinguishes them). Conversations can only be created via RPC — `start_dm_conversation(p_other_user_id)` (dedupes per pair of people, whichever direction you message from) or `start_marketplace_conversation(p_listing_id)` (dedupes per buyer+seller+**listing**, since a buyer messaging the same seller about a different item should get a separate thread). `conversations.listing_id` (nullable FK to `listings`) was added via `ALTER TABLE` once `listings` existed.
- `listings`, `listing_media` — marketplace. Same immutable-content convention as posts/comments/messages: title/description/price/category/condition can't be edited after creation, only `status` transitions (`active` → `sold`/`removed`, `sold` → `active` to relist). `category` and `condition` are fixed check-constraint enums (see `packages/shared/src/schemas/listing.ts` for the values) — adding a new one needs a migration, not just a frontend change.
- `professors`, `courses`, `professor_courses`, `reviews`, `review_votes`, `review_reports`, `entity_submissions` — Reviews. `professors`/`courses` are **centrally managed**: no client INSERT/UPDATE policy at all, the only ways a row can exist are a seed migration or the `admin_review_entity_submission(p_submission_id, p_decision, p_merge_into_id?)` RPC — staff-wide for `professor`/`course` submissions, **admin-only** for `community` submissions (a guard added inside the RPC itself during the admin dashboard build, alongside extending `entity_submissions.type` to include `'community'`). `reviews` follows the immutable-content convention (only `status` may change: `pending`→`visible`→`hidden`/`removed`); a partial unique index (`reviews_one_active_per_target`, excludes `status='removed'`) is what lets a user remove their own review and post a fresh one for the same target without allowing two _active_ reviews. `reviewer_id` is stored but never selected by the app's public queries — reviews are anonymous-to-other-students by design (app-layer guarantee, not an RLS column-level one — see the comment on `ReviewPublic` in `packages/shared/src/types.ts`). A `BEFORE INSERT` trigger forces `status='pending'` for brand-new accounts (<3 days old) or bodies that look like they contain an email/phone number (`flagged_pii`); `review_reports` auto-hides a review at 2+ reports. `trending_score` is a recency-decayed sum over each target's helpful-vote-weighted reviews (see `compute_trending_score` in `20260902270200_reviews_trending.sql`), recomputed hourly via **pg_cron** (`recompute-review-trending-scores` job) — explicitly not just average rating, per the original ask.
- **Course-review detail** (`20260902270500_course_review_detail.sql`, `20260902270600_course_detail_page_fields.sql`): a course review can carry four course-only sub-ratings — `interest_rating`, `difficulty_rating`, `workload_rating`, `teaching_rating` (all 1–5, all null for professor reviews — enforced by `validate_review_subratings`) — plus an optional `taught_by_professor_id` (must be one of the course's linked `professor_courses`) **or**, mutually exclusively, a free-text `alternate_professor_name` (`20260902300000_review_alternate_teacher.sql`) for when the reviewer's actual teacher isn't linked to the course at all — see §10's Reviews entry and the "Teacher mentions" admin tab. `courses.avg_interest`/`avg_difficulty`/`avg_workload`/`would_recommend_pct` and `professors.would_recommend_pct` are trigger-maintained the same way `avg_rating` always was. A module coordinator's **teaching rating is scoped to that module only** — computed live by the `course_teaching_ratings(p_course_id)` SQL function (avg `teaching_rating` grouped by `taught_by_professor_id`, visible reviews only), deliberately _not_ rolled into that professor's own `avg_rating` on their professor page. `courses` also carries seed-only "official catalogue" detail columns (`description`, `credits`, `student_effort_hours`, `delivery`, `level`, `grading`, `learning_outcomes`, `teaching_methods`, `assessment_breakdown` jsonb, `source_url`) and `professors.title`/`source_url` — all nullable, populated only by data seeding (never user-editable), and the course page simply omits a section when its fields are empty. `professor_courses.is_coordinator` exists but our seeding has no way to actually distinguish a coordinator from a co-teacher yet, so it defaults `true`.

- `notifications` — one row per event (post like/upvote, post comment, message, review-helpful vote, staff content moderation, report resolution), written only by triggers/RPCs on the tables/functions that already generate those events (`reactions`, `comments`, `messages`, `review_votes`, the posts/comments/listings/reviews moderation triggers, `resolve_report`) via a shared `create_notification()` SQL helper — no client INSERT policy exists at all. `link_path`/`preview` are denormalized at insert time (same reasoning as `conversations.last_message_body`). See §10 for the full breakdown, including a real ambiguous-FK-embed bug this surfaced and its fix.

**Deferred-column pattern** (used three times now — expect it again for Reviews if a table there ever needs to point at something not yet built): when table B needs to reference table A but A doesn't exist yet, ship B without the FK column, then `ALTER TABLE ... ADD COLUMN` once A exists. Used for `posts.community_id` and `conversations.listing_id`.

**Key SQL helper functions** (all `SECURITY DEFINER`, used inside RLS policies to avoid recursion — see comments in `20260902120300_auth_helpers.sql`):
`current_app_user_id()`, `current_university_id()`, `current_app_role()`, `is_staff()`, `is_active_user()`, `is_verified_user()`, `is_conversation_participant(id)`.

**RPCs callable from the client**: `resolve_university_for_email(email)`, `is_username_available(username)` (both pre-signup checks), `start_dm_conversation(other_user_id)`, `start_marketplace_conversation(listing_id)`.

**Storage buckets**: `post-media` and `listing-media` (both private, signed URLs, path `{university_id}/{owner_id}/{uuid}.ext`), `avatars` (**public**, deliberate tradeoff for simplicity — see comment in `20260902230000_avatars_storage.sql` — path `{university_id}/{user_id}/avatar.ext`, upsert overwrites).

**Realtime**: uses Supabase's `postgres_changes`. The `supabase_realtime` publication starts **empty** on a fresh project — tables must be explicitly added (`20260902240000_realtime_publication.sql` covers posts/comments/communities/community_members/conversations/messages; `20260902260000_marketplace.sql` adds `listings`; `20260902290000_notifications.sql` adds `notifications`). **If you add a new table that needs live updates, you must add it to this publication or subscriptions will silently never fire** — this exact bug existed undetected through steps 6–8 until caught and fixed in step 9. Realtime respects each table's RLS per subscriber.

## 6. Auth & UCD verification

- Supabase Auth (email/password). Signup flow: client pre-checks the email domain via `resolve_university_for_email()` RPC (friendly error) _before_ calling `supabase.auth.signUp()`.
- The real enforcement is a Postgres trigger (`handle_new_auth_user` in `20260902130000_auth_signup_trigger.sql`) on `auth.users` INSERT: resolves `university_id` from the email domain, and **raises an exception that aborts the whole signup transaction** if the domain isn't in any `universities.email_domains` array. Currently only `ucdconnect.ie` is seeded (`supabase/seed.sql`).
- Username + display_name are passed via `signUp({ options: { data: {...} } })` and read from `raw_user_meta_data` by the trigger.
- `email_verified_at` on `public.users` is kept in sync with Supabase's `email_confirmed_at` via a second trigger (`20260902130100_email_verification_sync.sql`).
- Frontend gating: `ProtectedRoute`/`PublicOnlyRoute` (`apps/web/src/components/ProtectedRoute.tsx`) check `session` + `isVerified` (from `useAuth()`).
- **Supabase dashboard setup required, not code**: Authentication → URL Configuration → Redirect URLs must include your dev/prod origins (e.g. `http://localhost:5173/**`) or verification/reset email links won't redirect correctly.

## 8. PWA / responsive

- `vite-plugin-pwa` configured in `apps/web/vite.config.ts`: manifest (name, brand-yellow theme color, icons, `id`, `categories`, `shortcuts` for Feed/Marketplace/Reviews), service worker (`generateSW` mode), `registerType: "autoUpdate"`.
- Icons generated once from the logo via a local Pillow script (not checked into repo as a script — one-off), output at `apps/web/public/icons/` (favicon 16/32, apple-touch-icon, standard + maskable 192/512).
- **The original `maskable-192.png`/`maskable-512.png` violated Android's maskable-icon safe zone** (found via pixel math, not visually — it looked fine at a glance): the bee artwork's bounding circle reached ~85% of the canvas radius, but a maskable icon's content must stay within the center 80% (Android crops the outer 20% into whatever shape the launcher wants — circle, squircle, teardrop). At 85%, a circular mask would clip the wingtip and antenna balls on real home screens. Regenerated both from the full-res source logo, scaled down so the artwork's content sits at ~72% radius (comfortable margin under 80%) on the same opaque yellow (`#F6BA24`) background. `icon-192.png`/`icon-512.png` (the non-maskable "any" purpose icons) didn't need this — they're not mask-cropped, so their existing edge-to-edge, transparent-background art is fine as-is.
- **Workbox runtime caching** (`vite.config.ts`'s `workbox.runtimeCaching`): Supabase Storage (avatars/post/listing media) via `StaleWhileRevalidate` (30-day expiration) — matches the immutable-content convention, so caching media indefinitely is safe; Supabase REST/RPC calls via `NetworkFirst` (4s timeout, 5-min cache) so an already-visited screen still renders something on a flaky/offline connection instead of erroring outright; Google Fonts stylesheet/webfonts via `StaleWhileRevalidate`/`CacheFirst`. `navigateFallback: "/index.html"` makes offline SPA navigation work. `workbox-window` had to be added as an explicit `apps/web` devDependency (not just a `vite-plugin-pwa` transitive dep) — pnpm's strict linking means `virtual:pwa-register/react`'s import of it doesn't resolve from the app's own node_modules otherwise, and the build fails at the Rolldown-resolve step, not at typecheck.
- **Install-prompt UX** (`components/InstallPrompt.tsx`): a custom banner is the only way to offer installation on Chrome/Edge/Android at all once `beforeinstallprompt`'s default is prevented (which suppresses their own mini-infobar) — captures the event, shows an "Install" button, remembers a dismissal for 14 days in `localStorage`. iOS Safari never fires that event (no programmatic install API exists there), so it gets a one-time "tap Share → Add to Home Screen" instructional banner instead, gated on UA sniffing + `!navigator.standalone`. **Mounted inside `AppShell` (post-login), not globally** — an earlier version mounted it in `main.tsx` so it showed on `/login` too, and a real headless-browser screenshot caught it completely covering the login form's Email/Password/Log-in button on a short viewport (`AuthLayout`'s screens are `min-h-dvh items-center justify-center`, so a `fixed` bottom banner has nothing to push against). `PwaUpdatePrompt.tsx` (a toast wrapping `virtual:pwa-register/react`'s `useRegisterSW`, offering a one-tap reload when a new service worker is waiting) is mounted the same way, same reason.
- **A real accessibility bug was found and fixed live via a Lighthouse pass**: `text-brand-purple` (#6529c9, used unremapped in ~19 places — links, prices, badges) and `text-stone-400` (used everywhere for secondary/muted text) both fell under WCAG AA's 4.5:1 contrast requirement against the dark-mode surface colors (~2.3-2.6:1 and ~3.7:1 respectively against `--color-white`'s dark value). Fixed the same way as every other dark-mode color in this codebase — a token remap, not per-component classes — by adding `--color-brand-purple: #a077e3` (same hue, lighter) and `--color-stone-400: #888891` to `.dark` in `index.css`. Caught because Lighthouse defaults to whatever `localStorage` theme is already set, and this repo's dark-mode default meant the fresh profile it audited rendered in dark mode.
- **The brand logo was audited as an image-delivery problem**: `public/brand/bee-logo.png` (361×361, 162KB) was being served at ≤56px display size everywhere, wasting ~140KB per page load. Rather than resize the canonical file in place (AGENTS.md points at that exact path/pixels for re-sampling brand colors — don't touch it), generated `bee-logo-sm.webp`/`.png` (192×192, ~14KB/~49KB) and added `components/BrandLogo.tsx` (a `<picture>` with WebP source + PNG fallback) used by all 5 call sites (`AppShell`, `AuthLayout`, `AdminLayout`, `LoadingScreen`). The original full-res PNG is `globIgnores`-excluded from the Workbox precache (nothing fetches it anymore) so it doesn't cost installs 160KB for nothing.
- **Google Fonts moved off a CSS `@import`** (`index.css`) **to `<link rel="preconnect">` + `<link rel="stylesheet">` in `index.html`**: a Lighthouse "network dependency tree" audit showed `@import` chaining serially (app CSS → googleapis CSS → gstatic font, ~220ms), because a CSS `@import` blocks that stylesheet's own parsing until it resolves; a `<link>` in the HTML is discoverable and fetchable in parallel with everything else instead.
- Mobile-first Tailwind layout throughout (`md:` breakpoint switches mobile → desktop chrome). No dedicated tablet breakpoint tuning done.
- **Real Lighthouse pass** (desktop preset, headless Chrome for Testing, against a `vite preview` production build of `/login`): **Performance 100 / Accessibility 100 / Best Practices 100 / SEO 66**. The SEO score is intentionally not 100 — `public/robots.txt` was added as `Disallow: /` because every page on this platform is behind UCD-email-verified auth anyway; nothing here should be publicly indexed, so "blocked from indexing" is correct, not a bug. Mobile preset (simulated mid-tier throttling) scores Performance 89 — the gap is the existing single ~700KB JS bundle (already a known, documented, accepted tradeoff, see below), not something newly introduced or fixed here; route-based code-splitting beyond the existing admin-only lazy boundary would be the fix if this ever needs revisiting, per the narrow-exception convention in AGENTS.md.

## 10. Feature status in detail

**Feed** (`features/feed/`): text + single-photo posts, like (heart), comment (flat, non-threaded — `comments.parent_comment_id` column exists for future threading but unused), soft-delete own post (trigger blocks editing — only `deleted_at` may change). Realtime live updates. `PostCard` has a `mode="like" | "vote"` prop reused by both the main feed and communities.

**Anonymous posting/commenting**: `posts.is_anonymous`/`comments.is_anonymous`, immutable after creation (extended `prevent_post_body_changes`/`prevent_comment_body_changes`, same as every other content field). A `VenetianMask` toggle in `PostComposer` (feed + community posts) and `CommentSection`'s comment input lets the poster opt in per-post/per-comment — not a blanket "always anonymous" like Reviews. Reuses the Reviews anonymity convention deliberately (author hidden from other students, staff can still trace via the real, always-stored `author_id`) rather than inventing a new one, but the mechanism differs out of necessity: Reviews are *always* anonymous, so it can statically never `SELECT reviewer_id` in its public query; posts/comments mix anonymous and non-anonymous rows in the same feed/community query, so `features/feed/api.ts`'s `maskAnonymousAuthor` (used by `hydratePosts` and `fetchComments`) strips the author's name/avatar/username down to a generic "Anonymous" placeholder for anyone but the row's own author, at the earliest point the data leaves the API layer — before it ever reaches a hook or component. Same documented caveat as `reviews.reviewer_id` (see §11): this is an app-layer guarantee, not a column-level RLS one. `PostCard`/`CommentSection` show a small "(posted anonymously)" badge to the author's own view only (their own post/comment still renders normally to them). **A notification-leak check was done deliberately** (the founder specifically asked whether a comment-on-your-post notification could leak an anonymous commenter's identity): `notify_post_comment()` now passes a null `actor_id` when the triggering comment is anonymous, reusing the existing null-actor → neutral-icon rendering already built for `content_removed`/`report_resolved`; fixing this also surfaced and fixed a real second bug — `create_notification`'s own "never notify yourself" guard compares `recipient_id`/`actor_id`, which breaks once `actor_id` is nulled for anonymity (someone anonymously commenting on their *own* post would otherwise incorrectly self-notify), so `notify_post_comment` now also does its own explicit `v_post.author_id = new.author_id` skip. Verified live end-to-end with three disposable accounts (poster, commenter, and the post owner's notification), plus a direct SQL check confirming the immutability triggers actually block an `is_anonymous` UPDATE post-creation.

**Notifications** (`features/notifications/`, `pages/NotificationsPage.tsx`): one `notifications` table fed entirely by triggers on tables that already generate the events — no new client write path at all (mirrors the "SECURITY DEFINER trigger/RPC is the only mutation path" convention used everywhere else). Six event types: `post_like` (a 'like' or 'upvote' reaction on your post — downvotes don't notify), `post_comment` (someone comments on your post), `message` (a new DM/marketplace message, one notification per other participant), `review_helpful` (someone marks your review helpful), `content_removed` (staff remove/hide your post/comment/listing/review, or your review gets auto-hidden by the existing 2-report threshold), and `report_resolved` (a report you filed gets resolved/dismissed — notifies the reporter, not the content owner). `actor_id` is null for the last two (system-originated, not a person) — the frontend renders a neutral icon instead of an avatar when `actor` is null. `link_path`/`preview` are denormalized onto the row at insert time (same reasoning as `conversations.last_message_body`) so the list is a single query with one join (`actor:users`) instead of a type-dependent join per row. A shared `create_notification()` SQL helper centralizes the never-notify-yourself guard and is deliberately `REVOKE`d from `authenticated`/`anon` — unlike `resolve_report`/`admin_review_entity_submission` (meant to be called via RPC and self-gate with `is_staff()`), this one has no such check and would let any client insert an arbitrary notification into anyone's inbox with spoofed link/preview text if left directly callable.

A `/posts/:id` permalink page (`pages/PostPage.tsx`, reusing the existing `PostCard`/`CommentSection`) was added alongside this — needed so `post_like`/`post_comment`/moderation notifications have somewhere real to deep-link to (there wasn't one before; posts only ever rendered inline in the feed or a community page). `PostCard` gained a `defaultShowComments` prop so arriving from a notification lands with the comment thread already open. RLS on `posts` already handles visibility correctly for this (author can see their own moderated/removed post, restricted-community membership is enforced) — no new policy needed.

The Bell nav icon (`AppShell.tsx`) shows a live unread-count badge (capped at "9+"), backed by `useUnreadNotificationsCount()` — a `head: true` count query plus a realtime subscription, independent of whether the notifications list itself is mounted. Both that hook and `useNotifications()` open their own realtime channel; they're named with a `list`/`badge` suffix specifically so mounting both at once (e.g. AppShell's badge + the notifications page itself) doesn't try to double-subscribe the same channel name.

**A real bug was found and fixed live** while browser-testing this: the notifications list query originally embedded the actor as `actor:users(...)`, which PostgREST rejected as an ambiguous relationship — `notifications` has two FKs to `users` (`recipient_id` and `actor_id`), so an unqualified embed doesn't know which one to follow. Same class of issue as `posts`' `author:users!posts_author_id_fkey(...)` embed already in the codebase; fixed the same way (`actor:users!notifications_actor_id_fkey(...)`). The unread-count badge query has no join, so it kept working the whole time and masked this — worth remembering: a query with a join failing silently-to-the-user (just an error state) while a simpler nearby query on the same table succeeds isn't proof the feature works, it's proof only _that_ query works. Caught by an actual headless-browser click-through (two disposable accounts, one liking/commenting on the other's post, watching the badge update and then opening the notifications list), not by typecheck/lint/build, which all passed the whole time — this class of PostgREST embedding error isn't visible to TypeScript at all since the hand-authored `Database` type has no way to encode "this embed is ambiguous."

**"Someone else" teacher mentions** (`20260902300000_review_alternate_teacher.sql`): a course review's "who taught you?" picker has a third option beyond an existing linked professor or "not sure" — "Someone else (not listed above)", which reveals a free-text name input (`reviews.alternate_professor_name`, 1-160 chars trimmed). It's mutually exclusive with `taught_by_professor_id` (enforced in `validate_review_subratings`, same trigger that already gated sub-ratings/taught-by to course reviews only) and immutable after creation like every other review field (extended `prevent_review_content_changes`). The point isn't to let students free-form-attribute teaching credit — it's to surface, to staff, when the module's actual teacher doesn't match who's linked in `professor_courses` (a common real-world drift: coordinators change, guest lecturers cover a module, etc.). `review_alternate_teacher_mentions()` (a plain SQL function, not SECURITY DEFINER — relies on the existing `reviews` SELECT policy for both university-scoping and staff-only visibility of pending reviews, same reasoning as `course_teaching_ratings`) groups mentions by course + normalized (trimmed/lowercased) name, so "Jane Smith" and "jane smith " count as one mention, displaying the most-recently-submitted trimmed spelling. Surfaced read-only in a new "Teacher mentions" tab on `/admin/academics` (alongside the existing "Suggestions" tab, same tab-pattern as `AdminCommunitiesPage`/`AdminReviewsPage`) — staff judgment call from there, no in-app "link this professor" action was built (out of scope; use the existing `professor_courses` staff-write RLS policy directly, or Reviews' "Suggest entry" flow, if a change turns out to be warranted). Verified live end-to-end: real disposable accounts exercised all four trigger paths (insert succeeds, mutual-exclusion rejected, professor-review rejected, post-insert edit rejected) plus the grouping/normalization via direct SQL, and a full headless-browser click-through (sign in → write a review naming an unlisted teacher on a course with zero linked professors, confirming the picker/name-field render even then → confirm it appears on the review card → promote the account to admin → confirm the mention appears correctly in the new admin tab) before all test data was deleted.

**Dark mode** (`lib/ThemeProvider.tsx`, `lib/theme-context.ts`): Light/Dark/System, chosen from an "Appearance" card on the Profile page, persisted to `users.theme_preference` (defaults `'dark'` in the DB — new accounts land in dark mode) so it follows a student across devices, with `localStorage` as a same-device cache to avoid a flash-of-wrong-theme on load (a tiny synchronous inline script in `index.html`, reading `localStorage` before React mounts, sets the `dark` class on `<html>` immediately). **Transactional email (Resend)** (`supabase/functions/{auth-email,send-app-email,_shared}`, `supabase/migrations/20260903030000_email_notifications.sql`): every outbound email — Supabase Auth (signup confirmation, password reset, email change, invite, magic link, reauthentication) and app-triggered (community request approved/rejected, content removed by a moderator, a filed report resolved) — goes through Resend's REST API from server-side code only; the API key never reaches the frontend (`apps/web`'s `.env`/bundle has no email-related var at all). Two edge functions, no client-callable email endpoint:

- `functions/auth-email` is the target for Supabase's Auth **Send Email hook** — once wired up in the dashboard (see §12a), Supabase stops sending its own built-in auth emails entirely and POSTs the payload here instead. Verifies the Standard Webhooks signature (`SEND_EMAIL_HOOK_SECRET`), builds the `${SUPABASE_URL}/auth/v1/verify?token=...&type=...&redirect_to=...` confirmation link Supabase's own templates use, renders a branded template per `email_action_type`, sends via Resend.
- `functions/send-app-email` is a generic endpoint for in-app events, authenticated by a shared secret header (`x-internal-secret` / `INTERNAL_EMAIL_SECRET`) rather than a user JWT, since its only caller is Postgres itself via `pg_net` — never the browser.
- `functions/_shared/templates.ts` is the single place to add a new template (`renderAuthEmail` for auth action types, `renderAppEmail` for app event types); `_shared/layout.ts` is the shared branded HTML shell (bee logo, brand-yellow header, purple footer) every template renders into.

DB side: `public.create_notification()` (the existing shared helper every in-app notification already goes through, see the Notifications entry above) gained a trailing `p_send_email boolean default false` param — when true, it looks up the recipient's email and fires `public.trigger_transactional_email()`, which posts to `send-app-email` via `pg_net` (async, wrapped in its own exception handler so a Resend/network hiccup can never fail the transaction that triggered it — same "email is best-effort, not a correctness dependency" principle applied on both the Postgres and edge-function sides). Only the "you might miss this if you don't check the app" notification types opt in (`content_removed`, `report_resolved`, and the two new ones below) — routine ones (`post_like`, `post_comment`, `message`, `review_helpful`) stay in-app-only on purpose, to avoid emailing someone for every like. This left the original 6-argument `create_notification` overload untouched rather than rewriting it (see the migration's own comment) — both overloads coexist intentionally, a standard Postgres pattern for non-breaking signature extension.

`entity_submissions` community requests never generated an in-app notification at all before this (a real pre-existing gap — the requester had no way to find out except revisiting `/communities`). Fixed alongside the email work since it's the same code path: `notifications.type` gained `community_approved`/`community_rejected`, and `admin_review_entity_submission`'s community branch now calls `create_notification(..., p_send_email := true)` on both the approve and reject paths. `NotificationItem.tsx` renders both (icon + copy). Professor/course submission approval intentionally does **not** get this treatment (out of the founder's stated scope — community approval/rejection specifically was asked for) but the pattern is there to extend if that's ever wanted.

`email_log` (new table, staff-readable via `is_staff()`, no client write policy — every row comes from an edge function using the service-role key, same "only a trusted server-side path writes this" convention as `audit_log`/`notifications`) records every send attempt (category, event type, recipient, sent/failed, error message, Resend message id) for both auth and app emails — the error-handling/logging half of the ask. Nothing in the admin dashboard reads it yet (no `/admin/email-log` page was built — out of scope for this pass, but the table + RLS is ready for one).

**Settings page + account lifecycle** (`pages/SettingsPage.tsx`, `features/settings/`, reachable only from a "Settings" row on Profile): change password, privacy (who can message you, hide follower/following counts), blocked users, granular **email preferences**, "Download my data", and account deactivation/deletion. Every control here is wired to the backend, not static UI:

- **Account status gained two self-service states** (`users.status`: `active | suspended | banned | deactivated | deleted` — the first three existing, the last two new): **deactivate** hides your profile/content from others and is undone just by logging back in (`deactivate_own_account()`/`reactivate_own_account()` RPCs; `AuthProvider`'s `resolveAppUser()` calls the reactivate RPC automatically on load if a freshly-loaded profile is still `deactivated` — no separate confirmation screen, per the founder's explicit choice). **Delete** (`delete_own_account()` RPC) anonymizes the profile row immediately (display name/username/email/bio/avatar scrubbed, `status='deleted'`) but deliberately does **not** touch authored content — posts/comments/reviews/listings stay up, now attributed to "Deleted User" — a founder decision made explicitly to avoid the alternative (hard-deleting everything a student ever posted). `prevent_protected_user_field_changes` (the self-escalation trigger from step 14) was extended, not replaced, to allow exactly these self-transitions (`active↔deactivated`, `active|deactivated→deleted`) while still blocking a self-suspend/ban or touching an already-`deleted` row (deletion is terminal) — verified live with a disposable account, including that the guard still rejects a self-ban attempt.
- **`delete_own_account()` deliberately never calls `auth.admin.deleteUser()`**: `users.auth_user_id` references `auth.users(id) on delete cascade`, so deleting the auth row would cascade-delete the `users` row and, from there, every `posts`/`comments`/`reviews`/`listings` row via their own `on delete cascade` FKs — silently hard-deleting all of a student's content, the opposite of the chosen behavior. Instead, `supabase/functions/delete-account` (a new edge function, service-role) permanently **bans** the auth user (`admin.updateUserById(id, { ban_duration: "876000h" })`, ~100 years) after calling the RPC with the caller's own JWT, plus best-effort avatar-file cleanup. Worth remembering if "delete" ever needs revisiting: banning, not deleting, is what makes login-blocking compatible with content preservation here.
- **Email preferences** (`users.email_pref_{comments,likes,messages,community,marketplace,reviews,announcements}`, all boolean, **default OFF** — an explicit founder decision, extending the existing "don't email for every like" principle from step 13 rather than reversing it) turned the previously routine-only-in-app notification types (`post_like`/`post_comment`/`message`/`review_helpful`) into optional email categories too, alongside the existing "important" ones. The gating moved from each `notify_*` trigger (which used to hardcode `p_send_email`) into `create_notification()` itself: a new 8-arg overload takes a `p_email_category` and looks up the matching `email_pref_*` column before actually emailing — coexists with the 6-/7-arg overloads from steps 13/§10 above, same non-breaking-extension pattern. Security/verification emails (Supabase Auth's own — signup, recovery, etc.) have **no** preference column at all and stay mandatory, as decided; there's no "announcement broadcast" sender built yet, just the toggle, ready for one.
- **User-to-user blocking** (`blocked_users` table, mirrors the `follows`/`community_members` insert-or-delete convention): blocking is **mutual** — `is_blocked_pair()` filters a blocked author's posts/comments/listings out of the other party's `SELECT` policies (both directions, staff exempted for moderation), and `conversation_has_block()` stops either party from starting or continuing a DM (checked in `start_dm_conversation`/`start_marketplace_conversation` and the `messages` INSERT policy). A separate `is_author_visible()` helper (deactivated-only, not blocking) hides a **deactivated** user's posts/comments/listings/profile from everyone but themselves and staff — deleted accounts are deliberately *not* hidden this way, since their content is meant to stay visible. `users.who_can_message` (`everyone | following | nobody`) additionally gates `start_dm_conversation` only, not marketplace chat. All of the above verified live end-to-end with two disposable accounts (mutual block → both directions of `start_dm_conversation` correctly rejected → unblock → succeeds; `who_can_message='nobody'` correctly rejected) before cleanup.
- **"Download my data"** (`supabase/functions/export-data`, the synchronous-download approach, not an emailed link): a service-role-free edge function — every query runs as the caller via their own JWT, deliberately never touching the service role, so it can only ever return what RLS already lets that exact user see. Returns one JSON document (profile, posts, comments, reactions, listings, reviews, messages sent, conversation ids, follows both directions, blocks, notifications, feedback, community memberships, entity submissions); the frontend triggers an immediate browser download from the response, no background job or storage bucket involved.
- **Feedback (Request a Feature / Report a Bug)** (`features/feedback/`, a `feedback` table, `/admin/feedback`): reachable from Profile, not Settings, per the founder's ask. Same immutable-content convention as everywhere else (only `status`/`admin_note` may change after submission, staff-only). Every new submission also fires an email to `info@unibuzzz.com` via the existing `trigger_transactional_email()`/Resend pipeline (`notify_new_feedback` trigger) — same best-effort, never-fails-the-insert behavior as every other app email here, so it'll silently no-op until the §12a Resend setup is done, same as the rest.

**Not yet done, needs a live pass on the email side specifically**: the DB/RLS/RPC side of all of the above (deactivate/reactivate/delete, blocking, feedback, the email-preference gating logic) *was* exercised live against the real Supabase project this session (migration pushed, both new edge functions deployed and confirmed to require auth, disposable-account tests for every path above, all cleaned up afterward) — but actually receiving an email for any of these still depends on the same unfinished §12a Resend/Vault setup as the rest of this codebase's email system. Nothing new to configure beyond §12a; once that's done, these categories start sending like any other.

## 11. Known issues / gotchas for whoever picks this up

- **Supabase CLI auth can silently point at the wrong account**: `supabase db push`/`db query` can fail with a 403 ("account does not have the necessary privileges") even when a `supabase login` session already exists, if that session belongs to a different Supabase account/org than the one owning this project (`oaseqfvqdlvuhkcvobbg` / "Unibuzzz"). `supabase projects list` shows which projects the current session can actually see — if "Unibuzzz" isn't in that list, the fix is a fresh personal access token (from supabase.com/dashboard/account/tokens) for the account that owns it, exported as `SUPABASE_ACCESS_TOKEN` for the session, not re-running `supabase login` and hoping. Hit this at the very start of this session; cost real back-and-forth to diagnose.
- **Bundle size warning** at build time (`chunks are larger than 500 kB`) — no code-splitting done yet. Fine for now, revisit if it becomes a real problem (route-based `lazy()` would be the fix).
- **Known false-positive lint warning**: oxlint's React Compiler ref-lint rule flags `PostComposer.tsx`'s `handleSubmit(onSubmit)` line as "cannot access refs during render" — investigated, it's a false positive from how the rule interacts with react-hook-form's `handleSubmit`; the ref (`fileInputRef`) is genuinely only touched inside event handlers. Left as-is, don't waste time re-chasing it.
- **RLS + UPDATE gotcha** (bit us once, will bite again if forgotten): Postgres RLS requires an UPDATE's _resulting_ row to still satisfy the table's SELECT policy, not just the UPDATE policy. This means a SELECT policy that hides soft-deleted rows will **silently block the very UPDATE that soft-deletes them** unless the actor (e.g. the post's author) is exempted in the SELECT policy too. See the fix in `posts`/`comments` SELECT policies (`author_id = current_app_user_id()` is OR'd in). `listings` and `reviews` were built with this pre-empted from the start and verified live.
- **RLS + multiple UPDATE policies gotcha** (found live while building Reviews — see `20260902270300_fix_review_moderation_policy.sql`; recurred and was fixed again on `posts`/`comments`/`listings` during the admin dashboard build, see `20260902280200_fix_moderation_policy_gaps.sql`): when a table has more than one permissive UPDATE policy (e.g. "owner can do X" + "staff can do Y"), Postgres combines **all** policies' `USING` clauses with OR, and **separately** combines **all** policies' `WITH CHECK` clauses with OR — not paired per-policy. If policy A's `WITH CHECK` is deliberately narrow (e.g. "owner may only set status to 'removed'") but policy B's `WITH CHECK` is looser (e.g. only checks `university_id`, forgetting to also require `is_staff()`), a non-staff owner's UPDATE can pass via policy A's `USING` and then slip through on policy B's under-restrictive `WITH CHECK` — bypassing policy A's restriction entirely. Confirmed live on `reviews` originally; the same pattern (missing `is_staff()` in a staff policy's `WITH CHECK`) was also found — not yet exploitable, since the owner's own policy already permitted everything reachable that way, but fixed anyway before the admin dashboard started actively relying on those policies — on `posts`/`comments`/`listings`. **Whenever an UPDATE policy narrows what an actor can set via `WITH CHECK`, audit every other UPDATE policy on that table to make sure its `WITH CHECK` re-asserts its own gate (e.g. `is_staff()`), not just the shared conditions.**
- **Self-escalation trigger blocks even a privileged bootstrap UPDATE** — `prevent_protected_user_field_changes` (`20260902120400_users_policies.sql`) fires on _any_ UPDATE to `users.role`/`status`, including one issued by a migration. Migrations run as the table-owning role, which bypasses RLS entirely, but **not** `BEFORE UPDATE` triggers — those aren't an RLS mechanism. To bootstrap the first real admin (or any other one-off privileged row change), wrap the UPDATE in `ALTER TABLE ... DISABLE TRIGGER users_protect_fields` / `... ENABLE TRIGGER ...` inside the migration, don't rely on `auth.uid()` resolving `NULL` outside a request context (it happens to also let the UPDATE through, but that's an accidental side effect of the trigger's own logic, not a documented guarantee). See `20260902280000_admin_bootstrap.sql`.
- **zod `.default()` breaks react-hook-form's resolver typing** — don't use `.default()` in a schema consumed by `useForm<T>()`; seed the default via `useForm`'s `defaultValues` instead. Hit this building the community-creation form; see comment in `packages/shared/src/schemas/community.ts`.
- **`Database` type structural requirements**: `packages/shared/src/supabase/database.types.ts` is hand-authored (no live-generated version has been produced yet). Every table needs `Relationships: [...]` (even if `[]`) and the schema object needs `Views: Record<string, never>` — omitting either silently breaks `.rpc()` argument typing in a confusing way (discovered the hard way; see git history / this session's transcript if it recurs). Once things stabilize, consider running `supabase gen types typescript --linked` to replace this file with a generated one and diff for drift.
- **Avatar bucket is public** (not signed URLs) — intentional tradeoff, documented in the migration, but worth knowing if privacy requirements tighten later.
- **Never call `auth.admin.deleteUser()` on this schema without checking cascades first**: `users.auth_user_id references auth.users(id) on delete cascade` means deleting an `auth.users` row cascades straight through to the matching `public.users` row, and from there to *every* `posts`/`comments`/`reviews`/`listings`/etc. row via their own `author_id`/`seller_id`/`reviewer_id` `on delete cascade` FKs — a silent, total hard-delete of everything that person ever posted. `delete_own_account()`/`supabase/functions/delete-account` deliberately use `admin.updateUserById(id, { ban_duration: ... })` instead (see §10) specifically to avoid this. Any future feature that needs to truly remove an `auth.users` row should audit the FK cascade chain from `users` outward first, not assume "delete the auth user" is harmless just because it's the obvious API.
- **Testing RLS/`SECURITY DEFINER` functions via `supabase db query --linked` without a real JWT**: that command connects as a privileged role, so `auth.uid()` normally resolves `NULL` and RLS is bypassed by ownership — neither reflects what a real authenticated client experiences. `select set_config('request.jwt.claims', json_build_object('sub','<auth_user_id>','role','authenticated')::text, false); set role authenticated;` as the first two statements of the same query makes `auth.uid()`/`current_app_user_id()`/etc. resolve exactly as they would for that real user, in the same connection, without needing to actually sign in and mint a token first. Used this session to verify deactivate/reactivate/delete and blocking end-to-end (see §10); each `db query` invocation is its own connection, so both `set_config` calls and the actual test statements must be in the *same* invocation, or the session state is lost.
- **Direct `auth.users` INSERT for disposable test accounts** (used throughout this repo's verification process) needs several `text` columns explicitly set to `''` rather than left `NULL` — `confirmation_token`, `recovery_token`, `email_change`, `email_change_token_new`, `email_change_token_current`, `phone_change`, `phone_change_token`, `reauthentication_token`. Leaving them `NULL` doesn't fail the insert but breaks GoTrue's own login query afterward with an opaque `"Database error querying schema"` — hit this building Reviews, cost real time to diagnose. Set all eight to `''` up front.
- **Column-level reviewer anonymity is app-layer, not RLS-layer**: Postgres RLS is row-level, not column-level. `reviews.reviewer_id` is a real column any same-university authenticated caller technically has SELECT privilege on (RLS just doesn't hide the _row_); the app simply never requests that column in its public queries (see `REVIEW_PUBLIC_SELECT` in `features/reviews/api.ts`). A real column-level guarantee would need `REVOKE`d column privileges plus a `SECURITY DEFINER` read surface for the few legitimate uses (the viewer's own "have I reviewed this"/"my reviews" filters) — deliberately not built this session (documented tradeoff, not an oversight). Worth doing properly alongside the general moderation system in step 14 if reviewer privacy needs to be a harder guarantee than "the shipped client doesn't ask for it."
- No tests exist anywhere in the repo (no test runner installed). Verification is: typecheck + lint + build + manual REST/RPC calls against the live Supabase project with disposable test accounts (created and cleaned up every time) + live Realtime checks + an actual headless-browser click-through of the built UI, screenshots reviewed, console checked for errors. This session's sandbox previously blocked elevating a disposable account to `moderator`/`admin` via the API layer (flagged as an open item in earlier revisions of this file) — worked around during the admin dashboard build by promoting test accounts directly via SQL (`UPDATE public.users SET role = ...`, same disable-trigger technique as the bootstrap migration, run through the Supabase CLI's `db query` against the linked project rather than through the app), which is not itself a sandbox-restricted action. Both `admin_review_entity_submission` paths (reject and approve) are now confirmed working live.

## 12a. Resend email setup (manual, not yet done)

The email code (§10's "Transactional email" entry) is written and typechecked but **not deployed or exercised live**. To turn it on:

1. **Resend account + domain**: sign up at resend.com, add your sending domain (`Domains` → `Add Domain`), and add the DNS records Resend shows you at your DNS provider — an SPF `TXT` record, a DKIM `CNAME`/`TXT` (usually `resend._domainkey`), and Resend also recommends a `DMARC` `TXT` record (`_dmarc`) even though it's not strictly required for sending. Wait for the domain to show **Verified** in Resend before continuing — sending from an unverified domain will fail or land in spam. Create an **API key** (`API Keys` → `Create API Key`, Sending access is enough).
2. **Deploy the two edge functions** (needs `SUPABASE_ACCESS_TOKEN` set per the CLI-auth gotcha in §11):
   ```
   pnpm dlx supabase functions deploy auth-email --project-ref oaseqfvqdlvuhkcvobbg
   pnpm dlx supabase functions deploy send-app-email --project-ref oaseqfvqdlvuhkcvobbg
   ```
3. **Set edge function secrets** (fill in real values in a local, gitignored copy of `supabase/functions/.env` — never commit it — then run):
   ```
   pnpm dlx supabase secrets set --project-ref oaseqfvqdlvuhkcvobbg --env-file supabase/functions/.env
   ```
   Required: `RESEND_API_KEY`, `RESEND_FROM_EMAIL` (e.g. `UniBuzzz <no-reply@mail.yourdomain>`, must be on the verified domain), `PUBLIC_SITE_URL` (the deployed web app's origin), `INTERNAL_EMAIL_SECRET` (any long random string, e.g. `openssl rand -hex 32`), `SEND_EMAIL_HOOK_SECRET` (from step 5 below — comes back once you enable the hook, so you'll set this one second, after step 5's `v1,whsec_...` value exists). `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` don't need setting — Supabase injects those into every deployed function automatically.
4. **Store the internal secret in Vault** (SQL Editor, run once, real value not committed anywhere): 
   ```sql
   select vault.create_secret('<same random string as INTERNAL_EMAIL_SECRET>', 'internal_email_secret');
   ```
   This is what `public.trigger_transactional_email()` reads to authenticate its `pg_net` call to `send-app-email` — see the migration's comment. If this step is skipped, app emails (community approval/rejection, moderation, report resolution) silently no-op (a `raise warning` in the Postgres logs, nothing breaks) — auth emails are unaffected either way, they go through a separate path (step 5).
5. **Enable the Auth Send Email hook**: Supabase dashboard → Authentication → Hooks → **Send Email** → point it at the deployed `auth-email` function → copy the secret it shows (`v1,whsec_...`) → set that as `SEND_EMAIL_HOOK_SECRET` (redo step 3's `secrets set` with it filled in). Once enabled, Supabase **stops sending its own built-in auth emails entirely** — everything (signup, recovery, invite, email change, magic link, reauthentication) routes through this function from that point on, so don't enable it until the function is actually deployed and the API key is live, or verification emails will start failing.
6. **Push the migration**: `pnpm dlx supabase db push` (adds `email_log`, wires the notification/email triggers — see §10).
7. **Test it end-to-end** (all of this needs steps 1–6 done first): sign up a disposable test account and confirm the branded confirmation email arrives; use "Forgot password" and confirm the reset email; as an admin, approve then reject a test community request and confirm both the in-app notification and the email land; check `email_log` (`select * from email_log order by created_at desc;`) and the Supabase dashboard's function logs (Edge Functions → auth-email / send-app-email → Logs) for any `status = 'failed'` rows or `console.error` output. Delete the test account/community afterward, per this repo's usual verification discipline (§11).
