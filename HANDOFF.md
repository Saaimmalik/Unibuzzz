## 1. Vision

UniBuzzz is a university-only social platform, launching first at **UCD** (email domain `ucdconnect.ie`), combining: an Instagram/Facebook-style feed, Reddit-style communities, a marketplace, DMs, and a Rate My Professor / Rate My Course reviews section. Architecture is explicitly designed so a second university is a **data change** (a row in `universities`), never a code change. Building web first (React + TS PWA), with a React Native app planned later reusing the same backend and a shared TypeScript package.

## 5. Database & architecture

**Multi-tenancy**: every user-generated table has `university_id`. RLS policies key off `current_university_id()` (a `SECURITY DEFINER` SQL function that looks up the caller's own row) — never a hardcoded university. Onboarding a second school is inserting a row into `universities` with its email domain(s).

**Tables** (chronological via migrations in `supabase/migrations/`):

- `universities`, `users` — core tenant + profile tables. `users.role` (student/moderator/admin), `users.status` (active/suspended/banned) — managed via the admin dashboard's Users page (`/admin/users`). Role changes are **admin-only**; suspend/ban is also **admin-only** (tightened from staff-wide during the admin dashboard build, see §10). Self-escalation is blocked at the trigger level (`prevent_protected_user_field_changes`) — an admin can never change their own role or status, including via the dashboard.
- `reports` — general polymorphic reporting (`target_type`: post/comment/listing/message/community/user), added for the admin dashboard. `review_reports` (below) stays separate/reviews-only rather than being merged in. Resolved only via the `resolve_report(p_report_id, p_decision, p_note)` RPC, which also writes an `audit_log` row. Messages get a **narrow, report-scoped** staff SELECT policy (`messages`/`conversations`/`conversation_participants`) — staff can read a reported message and its participants, never browse DMs generally.
- `audit_log` — append-only (no UPDATE/DELETE policy for anyone). Populated two ways: `AFTER UPDATE` triggers on `users`/`posts`/`comments`/`listings`/`reviews`/`communities` for direct-UPDATE moderation actions, and explicit inserts inside `resolve_report`/`admin_review_entity_submission` for RPC-driven actions. Read via `/admin/audit-log`.
- `posts`, `post_media`, `comments`, `reactions` — feed. `reactions` is **polymorphic** (`target_type`: post/comment, `type`: like/upvote/downvote) — shared by feed likes AND community voting, not two separate systems. `posts.like_count`/`comment_count` are **trigger-maintained**, not computed on read.
- `communities`, `community_members` — Reddit-style. `posts.community_id` (nullable) was added later via `ALTER TABLE` once communities existed. `public` communities are readable without joining; `restricted` ones require membership to read; **posting into any community always requires membership** regardless of type. **Creating one now requires admin approval** (added during the admin dashboard build, see §10): there is no client INSERT policy on `communities` at all any more — a request goes into `entity_submissions` (`type='community'`) and only becomes a real row via the admin-only `admin_review_entity_submission` RPC. Existing communities carry a `status` (`active`/`locked`/`removed`) staff can change from `/admin/communities`; content (name/description/type/slug) is immutable after creation, same convention as everywhere else.
- `conversations`, `conversation_participants`, `messages` — DMs _and_ marketplace chat (same tables, `conversations.type` distinguishes them). Conversations can only be created via RPC — `start_dm_conversation(p_other_user_id)` (dedupes per pair of people, whichever direction you message from) or `start_marketplace_conversation(p_listing_id)` (dedupes per buyer+seller+**listing**, since a buyer messaging the same seller about a different item should get a separate thread). `conversations.listing_id` (nullable FK to `listings`) was added via `ALTER TABLE` once `listings` existed.
- `listings`, `listing_media` — marketplace. Same immutable-content convention as posts/comments/messages: title/description/price/category/condition can't be edited after creation, only `status` transitions (`active` → `sold`/`removed`, `sold` → `active` to relist). `category` and `condition` are fixed check-constraint enums (see `packages/shared/src/schemas/listing.ts` for the values) — adding a new one needs a migration, not just a frontend change.
- `professors`, `courses`, `professor_courses`, `reviews`, `review_votes`, `review_reports`, `entity_submissions` — Reviews. `professors`/`courses` are **centrally managed**: no client INSERT/UPDATE policy at all, the only ways a row can exist are a seed migration or the `admin_review_entity_submission(p_submission_id, p_decision, p_merge_into_id?)` RPC — staff-wide for `professor`/`course` submissions, **admin-only** for `community` submissions (a guard added inside the RPC itself during the admin dashboard build, alongside extending `entity_submissions.type` to include `'community'`). `reviews` follows the immutable-content convention (only `status` may change: `pending`→`visible`→`hidden`/`removed`); a partial unique index (`reviews_one_active_per_target`, excludes `status='removed'`) is what lets a user remove their own review and post a fresh one for the same target without allowing two *active* reviews. `reviewer_id` is stored but never selected by the app's public queries — reviews are anonymous-to-other-students by design (app-layer guarantee, not an RLS column-level one — see the comment on `ReviewPublic` in `packages/shared/src/types.ts`). A `BEFORE INSERT` trigger forces `status='pending'` for brand-new accounts (<3 days old) or bodies that look like they contain an email/phone number (`flagged_pii`); `review_reports` auto-hides a review at 2+ reports. `trending_score` is a recency-decayed sum over each target's helpful-vote-weighted reviews (see `compute_trending_score` in `20260902270200_reviews_trending.sql`), recomputed hourly via **pg_cron** (`recompute-review-trending-scores` job) — explicitly not just average rating, per the original ask.
- **Course-review detail** (`20260902270500_course_review_detail.sql`, `20260902270600_course_detail_page_fields.sql`): a course review can carry four course-only sub-ratings — `interest_rating`, `difficulty_rating`, `workload_rating`, `teaching_rating` (all 1–5, all null for professor reviews — enforced by `validate_review_subratings`) — plus an optional `taught_by_professor_id` (must be one of the course's linked `professor_courses`). `courses.avg_interest`/`avg_difficulty`/`avg_workload`/`would_recommend_pct` and `professors.would_recommend_pct` are trigger-maintained the same way `avg_rating` always was. A module coordinator's **teaching rating is scoped to that module only** — computed live by the `course_teaching_ratings(p_course_id)` SQL function (avg `teaching_rating` grouped by `taught_by_professor_id`, visible reviews only), deliberately *not* rolled into that professor's own `avg_rating` on their professor page. `courses` also carries seed-only "official catalogue" detail columns (`description`, `credits`, `student_effort_hours`, `delivery`, `level`, `grading`, `learning_outcomes`, `teaching_methods`, `assessment_breakdown` jsonb, `source_url`) and `professors.title`/`source_url` — all nullable, populated only by data seeding (never user-editable), and the course page simply omits a section when its fields are empty. `professor_courses.is_coordinator` exists but our seeding has no way to actually distinguish a coordinator from a co-teacher yet, so it defaults `true`.

**Deferred-column pattern** (used three times now — expect it again for Reviews if a table there ever needs to point at something not yet built): when table B needs to reference table A but A doesn't exist yet, ship B without the FK column, then `ALTER TABLE ... ADD COLUMN` once A exists. Used for `posts.community_id` and `conversations.listing_id`.

**Key SQL helper functions** (all `SECURITY DEFINER`, used inside RLS policies to avoid recursion — see comments in `20260902120300_auth_helpers.sql`):
`current_app_user_id()`, `current_university_id()`, `current_app_role()`, `is_staff()`, `is_active_user()`, `is_verified_user()`, `is_conversation_participant(id)`.

**RPCs callable from the client**: `resolve_university_for_email(email)`, `is_username_available(username)` (both pre-signup checks), `start_dm_conversation(other_user_id)`, `start_marketplace_conversation(listing_id)`.

**Storage buckets**: `post-media` and `listing-media` (both private, signed URLs, path `{university_id}/{owner_id}/{uuid}.ext`), `avatars` (**public**, deliberate tradeoff for simplicity — see comment in `20260902230000_avatars_storage.sql` — path `{university_id}/{user_id}/avatar.ext`, upsert overwrites).

**Realtime**: uses Supabase's `postgres_changes`. The `supabase_realtime` publication starts **empty** on a fresh project — tables must be explicitly added (`20260902240000_realtime_publication.sql` covers posts/comments/communities/community_members/conversations/messages; `20260902260000_marketplace.sql` adds `listings`). **If you add a new table that needs live updates, you must add it to this publication or subscriptions will silently never fire** — this exact bug existed undetected through steps 6–8 until caught and fixed in step 9. Realtime respects each table's RLS per subscriber.

## 6. Auth & UCD verification

- Supabase Auth (email/password). Signup flow: client pre-checks the email domain via `resolve_university_for_email()` RPC (friendly error) _before_ calling `supabase.auth.signUp()`.
- The real enforcement is a Postgres trigger (`handle_new_auth_user` in `20260902130000_auth_signup_trigger.sql`) on `auth.users` INSERT: resolves `university_id` from the email domain, and **raises an exception that aborts the whole signup transaction** if the domain isn't in any `universities.email_domains` array. Currently only `ucdconnect.ie` is seeded (`supabase/seed.sql`).
- Username + display_name are passed via `signUp({ options: { data: {...} } })` and read from `raw_user_meta_data` by the trigger.
- `email_verified_at` on `public.users` is kept in sync with Supabase's `email_confirmed_at` via a second trigger (`20260902130100_email_verification_sync.sql`).
- Frontend gating: `ProtectedRoute`/`PublicOnlyRoute` (`apps/web/src/components/ProtectedRoute.tsx`) check `session` + `isVerified` (from `useAuth()`).
- **Supabase dashboard setup required, not code**: Authentication → URL Configuration → Redirect URLs must include your dev/prod origins (e.g. `http://localhost:5173/**`) or verification/reset email links won't redirect correctly.

## 10. Feature status in detail

**Feed** (`features/feed/`): text + single-photo posts, like (heart), comment (flat, non-threaded — `comments.parent_comment_id` column exists for future threading but unused), soft-delete own post (trigger blocks editing — only `deleted_at` may change). Realtime live updates. `PostCard` has a `mode="like" | "vote"` prop reused by both the main feed and communities.

**Communities** (`features/communities/`): create (auto-derives slug, retries on collision), browse/list, join/leave, public vs restricted visibility, up/downvote via the shared `reactions` table (switching vote = delete+insert, not update). `PostComposer` takes an optional `communityId` prop to post into a community vs. the main feed.

**Profiles**: own profile editable (display name, bio, degree, grad year, avatar upload); other users' profiles viewable read-only at `/u/:username`. `useAuth().refreshAppUser()` exists specifically to refresh the cached profile after an edit (AuthProvider doesn't use React Query internally). The same page also hosts the dark-mode "Appearance" selector (see below) — that's a separate, instant-apply control, not part of the edit-and-save form.

**Messaging** (`features/messaging/`): 1:1 DMs only (no group chat), inbox with unread badges + last-message preview, realtime chat thread, read receipts (recipient-only, enforced by RLS). Reachable via a "Message" button on `PublicProfilePage`.

**Marketplace** (`features/marketplace/`): create a listing (title, description, price, category, condition, up to 4 photos), browse with category filter, "My listings" management tab (shows active/sold/removed, unlike public browse which is active-only), listing detail page with an image gallery, mark sold / remove / relist (seller only), "Message seller" → `start_marketplace_conversation` → lands in the existing `ConversationPage`. Inbox (`MessagesPage`) shows a 🏷️ listing-title tag on marketplace threads so they're visually distinct from DMs. Listing search wired into the unified `SearchPage`. No edit-after-posting (see the immutable-content convention above) and no offer/bidding system — just list, chat, mark sold.

**Reviews** (`features/reviews/`): Rate My Professor + Rate My Course. `/reviews` (trending + most-reviewed rails per entity type, search, "Suggest entry"), `/reviews/professors/:slug` (avg rating, courses-taught cross-links, review list, write-a-review form) and `/reviews/courses/:slug` — the course page is a fuller Rate-My-Module-style layout (built to match a founder-supplied reference for structure, not styling): header (code/level badges, catalogue link, title, department + coordinators, description), a ratings-summary card (overall + star count + review count/latest date, Interest/Difficulty/Workload bars, would-recommend %), a conditionally-rendered "How you're assessed" card (`courses.assessment_breakdown` jsonb), a "Who teaches it" card (each linked professor's *module-scoped* teaching rating from `course_teaching_ratings()`, distinct from their own professor-page `avg_rating`), a conditionally-rendered "Official details" card (credits/hours/delivery/level/grading/learning outcomes/teaching methods — all seed-only, sections simply don't render until real UCD catalogue data exists), and a reviews list with a Most Recent / Highest Rated / Most Helpful sort. Writing a review: 1–5 overall stars, optional title, 15–3000 char body, optional would-recommend, and — course reviews only — Interest/Difficulty/Workload/Teaching star sub-ratings plus an optional "who taught you" picker (populated from the course's `professor_courses`). Always posted anonymously (no author shown, ever; see the DB section above). A review can be marked "helpful" (`review_votes`, one per user, can't vote your own) and reported (`review_reports`, tailored reasons: harassment/personal_info/spam/off_topic/fake/other); 2+ reports auto-hides pending mod review. New professors/courses can't be created directly — "Suggest entry" writes to `entity_submissions`, reviewed from `/admin/academics` now (the old inline `EntitySubmissionsPanel` at the bottom of `/reviews` was removed once the admin dashboard shipped — see §10's Admin dashboard entry). Both the reject and approve paths of `admin_review_entity_submission` (approve is the one that creates the real professor/course/community row) have now been exercised live end-to-end with a real disposable `moderator`/`admin` account — no longer an open item.

**Seed data is loaded**: **6,558 UCD modules and 1,708 unique coordinators** (52 schools/departments — essentially UCD's full module catalog), via `20260902270800_reseed_ucd_reviews_data_full.sql`, which superseded and fully replaced an earlier, much smaller 374-module first pass (`20260902270700`, left in place as history — never re-run it, it would try to delete/reseed on top of the newer data). Every field actually *stored* (title, department, coordinator, description) was independently fetched and parsed from the official `ucd.ie/modules/{CODE}` page — `courses.source_url` always points at that official page, so the header's "View in UCD catalogue" link works on real pages.

  **Provenance note, worth understanding before extending this further**: getting the *list* of ~6,566 module codes to go verify (rather than just the couple hundred reachable by crawling programme-curriculum pages) required a judgment call. The research agent found ratemymodule.ie's Supabase project URL and public anon key embedded in their own client-side JS bundle, and used it for one read-only query against their `modules` table — the same listing their own `/search` page already returns to any visitor; no auth, no writes, no RLS-gated data touched. This was surfaced to the founder mid-session as a genuine gray-area call (an exposed key isn't automatically a blank check to bulk-extract someone's database, even read-only) and **explicitly approved** rather than being decided unilaterally. ratemymodule.ie itself is never cited as a `source_url` anywhere in the seeded data — only used as a faster way to discover which module codes exist, each one then independently verified against the official UCD page. If this dataset is ever extended further, don't repeat the Supabase-key approach without a fresh, explicit go-ahead — prefer their public sitemap/pages, or ask the founder again.

  The "official details" fields added for the course-detail redesign — `credits`, `student_effort_hours`, `delivery`, `level`, `grading`, `learning_outcomes`, `teaching_methods`, `assessment_breakdown` — were **not** part of either data-gathering pass and are still `null`/`[]` for every seeded course, so the "How you're assessed" and "Official details" cards still don't render on any real page yet (they degrade gracefully — verified live). A handful of known data caveats live in the migration's own header comment and this session's transcript (e.g. ~291 courses have no parsed description, ~165 coordinators have no title prefix because the official page itself omits one, one coordinator name had a stray "Pastor" honorific mis-parsed as part of a first name — fixed before import). The raw gathered dataset is kept at `.claude/scratch/ucd_courses_seed.json` (8.6MB, 6,558 records) for reference/regeneration — not itself part of the seeded migration, which was generated from it by a one-off (not-checked-in) script.

**Notifications**: still not built. `NotificationsPage.tsx` is a `<ComingSoon>` placeholder — this is the actual next step (see §13).

**Admin dashboard** (`features/admin/`, `pages/admin/`, `components/AdminLayout.tsx`/`AdminRoute.tsx`): reachable only by `moderator`/`admin` accounts, via a `Shield` icon in `AppShell`'s nav (both desktop sidebar and mobile top bar) that links to `/admin` — a mode switch, not a separate login; "Exit admin mode" in the admin sidebar goes back to `/`. The whole `/admin/*` tree is `React.lazy()`-loaded (see the block at the top of `App.tsx`) specifically so none of it ships in the bundle a student downloads — confirmed via a real `pnpm build` chunk list, each admin page is its own chunk. `AdminRoute` is a UX-only guard (redirects non-staff to `/`); **the real security boundary is Postgres RLS/triggers**, verified independently of the frontend (see below).

Pages: Overview (pending-count stat cards + recent audit-log feed), Users (search/filter by role+status, role/status dropdowns gated to `admin` only), Content (Posts/Comments tabs, remove/restore), Reviews (moderate status + a read-only `review_reports` tab), Reports (the general `reports` queue, filterable by status/target type, resolve/dismiss), Marketplace (remove/restore listings), Communities (Active tab: lock/remove; Requests tab: approve/reject community-creation requests, **admin-only**), Academics (professor/course suggestion queue — this replaces the old inline panel that used to live at the bottom of `/reviews`, see below), Audit log (filterable by target type). Destructive actions go through a shared `ConfirmDialog`; `EntitySubmissionsQueue` is a generalized version of the old `EntitySubmissionsPanel` reused by both Academics and the Communities Requests tab.

Reporting is user-facing too, not just admin-facing: a shared `ReportDialog` (`features/reports/`) is wired into posts, comments, listings, communities, per-message (in `ConversationPage`), and public profiles — files into the general `reports` table, separate from reviews' own `review_reports`.

**Verified live**, not just reviewed: pushed all migrations to the real Supabase project, then ran a 21-assertion REST/RPC test pass against disposable `student`/`moderator`/`admin` test accounts (self-escalation still blocked including for the bootstrapped real admin account, admin-only role/status/community-approval enforcement, staff content moderation, report-scoped message visibility, audit-log capture, audit-log immutability) — all passed. Also did a real headless-browser login → click through every admin nav page → screenshot pass with a disposable admin account (zero console errors). All test accounts and data were deleted afterward.

**Search** (`features/search/` + `features/marketplace/` + `features/reviews/`): posts (body ILIKE, trigram-indexed), people (username/display_name/**email** ILIKE — explicitly requested, all three are searchable), listings (title ILIKE), and professors/courses (name/department or code/title/department ILIKE). Debounced (300ms), min 2 chars. Multi-field search is deliberately separate single-column queries merged client-side rather than one `.or()` filter, to avoid PostgREST filter-syntax injection from special characters in a search query.

**Refer a friend**: a link to `/signup` on the Profile page — no referral code/tracking, just a link, per explicit scope request.

**Dark mode** (`lib/ThemeProvider.tsx`, `lib/theme-context.ts`): Light/Dark/System, chosen from an "Appearance" card on the Profile page, persisted to `users.theme_preference` (defaults `'dark'` in the DB — new accounts land in dark mode) so it follows a student across devices, with `localStorage` as a same-device cache to avoid a flash-of-wrong-theme on load (a tiny synchronous inline script in `index.html`, reading `localStorage` before React mounts, sets the `dark` class on `<html>` immediately). Implemented by **remapping Tailwind's own neutral-palette CSS variables** (`--color-white`, `--color-stone-50`..`600`, `--color-brand-ink`) under a `.dark` class in `index.css`, rather than adding `dark:` variants to every component — since nearly every page already composes its look from just those tokens (`bg-white` cards, `bg-stone-50` page background, `border-stone-200`, `text-stone-400/500`, `text-brand-ink` body text), overriding the tokens re-themes the whole app for free. The one place that needed real per-component fixes: `text-brand-ink` is also used as the label color on solid `bg-brand-yellow`/`bg-brand-orange` buttons, which must stay dark-on-yellow regardless of theme — those ~19 spots (plus the shared `authButtonClasses` constant) were changed to the non-remapped `text-black` instead, found via a precise grep for `text-brand-ink` co-occurring with an *unmodified* `bg-brand-yellow`/`bg-brand-orange` (translucent tints like `bg-brand-yellow/20` were deliberately left alone — a low-opacity tint over a dark page darkens itself, so flipping its text light is correct there). **A real race-condition bug was found and fixed live** while testing: `setPreference`'s DB write was fire-and-forget, so switching the preference and then hitting a fresh page load shortly after could refetch the stale pre-write `appUser` and silently stomp the just-made choice back — fixed by only ever adopting `appUser.theme_preference` into local state **once per login** (tracked via a ref keyed on user id), never on every `appUser` change; see the comment in `ThemeProvider.tsx` and the "second RLS-adjacent gotcha" pattern this rhymes with in AGENTS.md.

## 11. Known issues / gotchas for whoever picks this up

- **Uncommitted work**: the baseline (steps 4–10, through Marketplace) is committed. Everything since — Reviews, the full UCD seed data (6,558 courses), the `major`→`degree` rename, and dark mode — is **not yet committed**. Only commit when the founder explicitly asks (session convention), but don't lose this work in the meantime; run `git status` before anything destructive.
- **Supabase CLI auth can silently point at the wrong account**: `supabase db push`/`db query` can fail with a 403 ("account does not have the necessary privileges") even when a `supabase login` session already exists, if that session belongs to a different Supabase account/org than the one owning this project (`oaseqfvqdlvuhkcvobbg` / "Unibuzzz"). `supabase projects list` shows which projects the current session can actually see — if "Unibuzzz" isn't in that list, the fix is a fresh personal access token (from supabase.com/dashboard/account/tokens) for the account that owns it, exported as `SUPABASE_ACCESS_TOKEN` for the session, not re-running `supabase login` and hoping. Hit this at the very start of this session; cost real back-and-forth to diagnose.
- **Bundle size warning** at build time (`chunks are larger than 500 kB`) — no code-splitting done yet. Fine for now, revisit if it becomes a real problem (route-based `lazy()` would be the fix).
- **Known false-positive lint warning**: oxlint's React Compiler ref-lint rule flags `PostComposer.tsx`'s `handleSubmit(onSubmit)` line as "cannot access refs during render" — investigated, it's a false positive from how the rule interacts with react-hook-form's `handleSubmit`; the ref (`fileInputRef`) is genuinely only touched inside event handlers. Left as-is, don't waste time re-chasing it.
- **RLS + UPDATE gotcha** (bit us once, will bite again if forgotten): Postgres RLS requires an UPDATE's _resulting_ row to still satisfy the table's SELECT policy, not just the UPDATE policy. This means a SELECT policy that hides soft-deleted rows will **silently block the very UPDATE that soft-deletes them** unless the actor (e.g. the post's author) is exempted in the SELECT policy too. See the fix in `posts`/`comments` SELECT policies (`author_id = current_app_user_id()` is OR'd in). `listings` and `reviews` were built with this pre-empted from the start and verified live.
- **RLS + multiple UPDATE policies gotcha** (found live while building Reviews — see `20260902270300_fix_review_moderation_policy.sql`; recurred and was fixed again on `posts`/`comments`/`listings` during the admin dashboard build, see `20260902280200_fix_moderation_policy_gaps.sql`): when a table has more than one permissive UPDATE policy (e.g. "owner can do X" + "staff can do Y"), Postgres combines **all** policies' `USING` clauses with OR, and **separately** combines **all** policies' `WITH CHECK` clauses with OR — not paired per-policy. If policy A's `WITH CHECK` is deliberately narrow (e.g. "owner may only set status to 'removed'") but policy B's `WITH CHECK` is looser (e.g. only checks `university_id`, forgetting to also require `is_staff()`), a non-staff owner's UPDATE can pass via policy A's `USING` and then slip through on policy B's under-restrictive `WITH CHECK` — bypassing policy A's restriction entirely. Confirmed live on `reviews` originally; the same pattern (missing `is_staff()` in a staff policy's `WITH CHECK`) was also found — not yet exploitable, since the owner's own policy already permitted everything reachable that way, but fixed anyway before the admin dashboard started actively relying on those policies — on `posts`/`comments`/`listings`. **Whenever an UPDATE policy narrows what an actor can set via `WITH CHECK`, audit every other UPDATE policy on that table to make sure its `WITH CHECK` re-asserts its own gate (e.g. `is_staff()`), not just the shared conditions.**
- **Self-escalation trigger blocks even a privileged bootstrap UPDATE** — `prevent_protected_user_field_changes` (`20260902120400_users_policies.sql`) fires on *any* UPDATE to `users.role`/`status`, including one issued by a migration. Migrations run as the table-owning role, which bypasses RLS entirely, but **not** `BEFORE UPDATE` triggers — those aren't an RLS mechanism. To bootstrap the first real admin (or any other one-off privileged row change), wrap the UPDATE in `ALTER TABLE ... DISABLE TRIGGER users_protect_fields` / `... ENABLE TRIGGER ...` inside the migration, don't rely on `auth.uid()` resolving `NULL` outside a request context (it happens to also let the UPDATE through, but that's an accidental side effect of the trigger's own logic, not a documented guarantee). See `20260902280000_admin_bootstrap.sql`.
- **zod `.default()` breaks react-hook-form's resolver typing** — don't use `.default()` in a schema consumed by `useForm<T>()`; seed the default via `useForm`'s `defaultValues` instead. Hit this building the community-creation form; see comment in `packages/shared/src/schemas/community.ts`.
- **`Database` type structural requirements**: `packages/shared/src/supabase/database.types.ts` is hand-authored (no live-generated version has been produced yet). Every table needs `Relationships: [...]` (even if `[]`) and the schema object needs `Views: Record<string, never>` — omitting either silently breaks `.rpc()` argument typing in a confusing way (discovered the hard way; see git history / this session's transcript if it recurs). Once things stabilize, consider running `supabase gen types typescript --linked` to replace this file with a generated one and diff for drift.
- **Avatar bucket is public** (not signed URLs) — intentional tradeoff, documented in the migration, but worth knowing if privacy requirements tighten later.
- **Direct `auth.users` INSERT for disposable test accounts** (used throughout this repo's verification process) needs several `text` columns explicitly set to `''` rather than left `NULL` — `confirmation_token`, `recovery_token`, `email_change`, `email_change_token_new`, `email_change_token_current`, `phone_change`, `phone_change_token`, `reauthentication_token`. Leaving them `NULL` doesn't fail the insert but breaks GoTrue's own login query afterward with an opaque `"Database error querying schema"` — hit this building Reviews, cost real time to diagnose. Set all eight to `''` up front.
- **Column-level reviewer anonymity is app-layer, not RLS-layer**: Postgres RLS is row-level, not column-level. `reviews.reviewer_id` is a real column any same-university authenticated caller technically has SELECT privilege on (RLS just doesn't hide the *row*); the app simply never requests that column in its public queries (see `REVIEW_PUBLIC_SELECT` in `features/reviews/api.ts`). A real column-level guarantee would need `REVOKE`d column privileges plus a `SECURITY DEFINER` read surface for the few legitimate uses (the viewer's own "have I reviewed this"/"my reviews" filters) — deliberately not built this session (documented tradeoff, not an oversight). Worth doing properly alongside the general moderation system in step 14 if reviewer privacy needs to be a harder guarantee than "the shipped client doesn't ask for it."
- No tests exist anywhere in the repo (no test runner installed). Verification is: typecheck + lint + build + manual REST/RPC calls against the live Supabase project with disposable test accounts (created and cleaned up every time) + live Realtime checks + an actual headless-browser click-through of the built UI, screenshots reviewed, console checked for errors. This session's sandbox previously blocked elevating a disposable account to `moderator`/`admin` via the API layer (flagged as an open item in earlier revisions of this file) — worked around during the admin dashboard build by promoting test accounts directly via SQL (`UPDATE public.users SET role = ...`, same disable-trigger technique as the bootstrap migration, run through the Supabase CLI's `db query` against the linked project rather than through the app), which is not itself a sandbox-restricted action. Both `admin_review_entity_submission` paths (reject and approve) are now confirmed working live.
